# SuburbMates — Operations Responsibility and Follow-through Map

## Status and purpose

This is the authoritative operational responsibility map for the solo-operated SuburbMates service. It applies the owner decisions in the [Decision Log](./SuburbMates%20%E2%80%94%20Decision%20Log.md), the [Target State and Operating Authority](./SuburbMates%20%E2%80%94%20Target%20State%20and%20Operating%20Authority.md), and the [Complete User Journey Map](./SuburbMates%20%E2%80%94%20Complete%20User%20Journey%20Map.md).

Its purpose is simple: the operator does not run the pipeline. The system performs repeatable, bounded work and retains evidence. The operator decides only a genuine exception or a material request where a safe automatic decision is not justified.

This map records responsibilities; it does not itself enable an integration, sender, automatic decision, migration or deployment. **Current** means the repository has an implemented path. **Planned follow-through** means the behaviour is desirable but remains a separately scoped, tested change.

## Operating rules

1. An item appears as operator work only when this map names a specific human decision. Otherwise it is background evidence, a private status, or a system alert.
2. The system must carry out the permitted aftermath of a recorded decision: constrained state change, audit evidence, safe public projection and the allowed user-status update. It must not make a second discretionary decision.
3. A qualification result, claim, payment, email match, ABN result, tier, AI output or media proposal never independently establishes unrelated publication, ownership, trust, commercial or ranking state.
4. Bulk exclusions, repeated discovery events, missing customer contact, unsupported categories and historic evidence gaps are not an operator backlog. They remain queryable evidence for a future batch-improvement programme.
5. User-visible status is primarily in-product. `auth@suburbmates.com.au` may send only the approved transactional statuses; there is no general sender, dispatcher, marketing, public inbox or automatic retry loop.
6. Stripe and billing remain disabled. No row below creates a billing obligation or makes payment relevant to directory treatment.
7. HubSpot is an optional, one-way Decision Inbox: it may show one low-detail task for a genuine Ops decision, but every decision and all protected evidence remain in SuburbMates. A HubSpot outage never blocks an Ops outcome.

## What must not appear as operator work

- every raw discovered business, automatic exclusion or repeat event;
- a missing customer contact method or unsupported category;
- an historic evidence gap that requires a future batch-data programme;
- an automatic ABN refresh or a bulk ABN campaign;
- an email-delivery retry, marketing activity or general support handling loop;
- Stripe/payment, because billing is disabled; and
- a provider dashboard check that the system has not explicitly integrated and labelled with freshness/failure evidence.

## Implementation boundary and next control

The current implementation already covers several bounded follow-through actions: deterministic approved-source qualification, protected claim/profile/contact decisions, audit records, route revalidation, narrow status-message attempts, ABN evidence recording, moderated media state and database health checks.

The remaining control work is not to make every external service "real time." It is to create one scoped **Ops source and refresh contract** for every datum shown in Ops: source, refresh trigger/frequency, freshness label, failure state, retained evidence, whether it is an operator decision, and why it belongs in the console. That work must not expand the current communication, billing or automation boundaries without a separately approved issue.
